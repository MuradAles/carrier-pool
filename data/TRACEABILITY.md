# Day-11 traceability

Generated by `backend/scripts/generate_data.py`. **Provenance, stated exactly:** every number below is computed by that script from the same seeded load plan it writes the 132 JSON files from — not written by hand, and not read back out of the JSON. What ties the two together is `backend/scripts/validate_data.py`, which reconciles the emitted bytes against that plan appearance by appearance (miles, carrier rate, weight, equipment, status, stops, carrier identity, and TMS B's running `pay` sum), and fails if they diverge. So: these numbers are true of the fixtures because the reconciliation passes, not because the table was derived from them.

The one thing it shares with the production code is geography: `app.domain.geo`'s hardcoded table and `app.domain.distance`'s Haversine x 1.2, deliberately, so the fixtures and the system agree on where places are. Everything the platform is actually judged on — the adapters, ingestion, the tier walk, scoring and pricing — is not imported here and did not exist when this table was computed. That is the point: it is an independent expectation to measure the system against, not an echo of it. Re-running the generator regenerates this file.

This is the source of the end-to-end assertions (TASKS.md H1) and the demo script.

## How to read a row, and what is asserted

For each day-11 load: the behavior it proves, the tier walk with the count at every
rung, the exact historical loads backing the accepted tier, the price arithmetic, and
the carrier ranking with each signal shown separately. A human with a calculator and
the sync files can reproduce all of it.

**Hard assertions** (these must hold exactly):

- the accepted tier and the load count backing it
- the identity of the top-ranked carrier
- median / p25 / p75 $/mi and the resulting price point and range
- lane-experience `n/(n+5)` and the deadhead distance for the top two carriers

**Reference-model parameters.** PRD section 8 fixes the five weights (0.35 / 0.20 /
0.15 / 0.20 / 0.10) and both cold-start formulas (DECISIONS D5), but leaves the
recency decay shape and the deadhead interpolation open. This table pins them:

```
experience = n / (n + 5)                                    # D5, saturating count
recency    = exp(-days_since_last_lane_load / 30)
equipment  = 1 if the carrier has ever hauled it, else 0    # 0.5 if the LOAD is UNKNOWN
deadhead   = clamp((250 - miles_from_last_delivery) / 200, 0, 1)   # full <=50, zero >=250
on_time    = (observed + lane_avg * 5) / (n + 5)            # D5, shrunk rate; D7 day-granular
score      = 100 * (0.35*exp + 0.20*rec + 0.15*equip + 0.20*deadhead + 0.10*on_time)
percentiles = PostgreSQL percentile_cont (linear interpolation)
```

If the implementation picks a different recency shape, the **ranking** assertions
still hold — every scenario below is built with a margin — but the absolute scores
will move. Assert on rank, tier, counts and price; treat scores as indicative.

## Cross-broker rate separation — the tenant-leak tripwire

Each broker prices to its own book `broker_a` cheap book (-0.05 $/mi), `broker_b` mid market (+0.30 $/mi), `broker_c` premium book (+0.68 $/mi).

So for every day-11 load below, the same lane key gives a **different** median in

repository layer ever drops `broker_id`, the reported $/mi and the p25–p75 range move

### What the generator asserts, and at what strength

1. **Always** — every own-vs-other-broker median gap on the same lane key is at least
   **0.15 $/mi**. Substituting another broker's history for yours
   changes the headline number, visibly. A regeneration that let two bands re-collide
   fails validation.
2. **Always** — pooling strictly increases the load count, which is why the provenance
   line has to report how many loads backed the answer.
3. **At `ZIP3` / `METRO`** — pooling moves at least **two of three** of
   (p25, median, p75) by >= 0.15 $/mi.
4. **At `REGION`** — pooling moves the median by >= 0.15 $/mi *or*
   widens the reported p25–p75 range by >= 1.5x.
5. **At `REGION_ANY`** — no money-level assertion, deliberately. See below.

### Two honest limits, both arithmetic rather than fixture weaknesses

**The middle band cannot separate on the median.** With three equally-sized blocks and
`broker_b` priced between the other two, the pooled *median* of the 3n loads necessarily
lands inside `broker_b`'s block — the 18th and 19th of 36 sorted values *are*
`broker_b`'s 6th and 7th. No arrangement of separated bands avoids that while keeping
the three medians apart. For `broker_b` the tell is the count and the range; for
`broker_a` and `broker_c` it is all three statistics.

**The wider the tier, the weaker the money signal.** One broker's own rates already span
~0.9 $/mi across haul lengths and equipment (short reefer vs long dry van), against an
inter-broker offset of 0.38. On a narrow key haul length barely varies and the bands are
disjoint; at `REGION` they overlap; at `REGION_ANY` — which *is* "the whole book, any
equipment" — three whole books look much like one, so the distribution test carries no
information and asserting it would be theatre. Closing that gap would need `broker_c` to
pay over $3/mi for long-haul dry van, which breaks the plausibility rule that matters
more. At `REGION_ANY` the leak is caught by the load count and the mandatory
low-confidence label, not by the price.

## Fixture-wide notes

- Miles come from `road_miles_between` (haversine × 1.2). Under DECISIONS D10 that
  makes Dallas→Houston 271 mi rather than the real-world 239. Every $/mi in this
  table is computed against those same miles, so the ratios are self-consistent.
- Every history load has `customer rate > carrier rate`. There are **no deliberate
  loss-making loads** in the fixture.
- All three brokers are structurally identical (DECISIONS D9) so tenant isolation is
  provable: broker A's answers must not move when B and C are ingested — and thanks
  to the separated rate bands above, if it *does* move, the number moves visibly.
- Rung coverage across the fixture: ZIP3 fires for the rich-lane and deadhead loads,
  METRO for the suburb-scatter and unknown-equipment loads, REGION for the thin-lane
  and (in brokers A and C) the flatbed cold-start load, and REGION_ANY for broker B's
  flatbed load. All four rungs of PRD section 7 have a fixture.
